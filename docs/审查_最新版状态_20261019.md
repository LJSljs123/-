## 四、新发现的工程缺陷：构建产物换行符不稳定

**现象**：在干净副本里重建，四个产物哈希与仓库版本全部不一致。

```
data.js       提交版 184155B / 重建版 190346B   （行数都是 6191）
structures.js 提交版 149552B / 重建版 154835B   （行数都是 5283）
cases.js      提交版  68513B / 重建版  70350B   （行数都是 1837）
story.js      提交版   9264B / 重建版   9534B   （行数都是  270）
```

**根因**：字节差 = 行数，即每行多 1 字节——换行符不同。

- 提交版：纯 LF（6191 行）
- 重建版：纯 CRLF（6191 行）
- `core.autocrlf=true` + `.gitattributes` 的 `* text=auto eol=lf` 让仓库与检出都是 LF
- 但 Python 的 `write_text()` 在 Windows 上默认 `newline=None` → `\n` 被写成 `\r\n`

**后果**：
1. 每次构建都会产生"全文件改动"的 git diff（噪音 6191 行），掩盖真实改动；
2. **"干净副本重建、哈希一致"这条答辩证据失效**——重建结果与提交版本哈希不同；
3. 昨天演练通过是因为当时工作区文件本身就是构建产出的 CRLF，今天 git 检出成 LF 才暴露。

**建议修法**（未执行）：所有产物写入改为 `write_text(..., newline="\n")`，或在 `.gitattributes` 对 `web/*.js` 设 `-text`（不做换行转换）。前者更彻底。
